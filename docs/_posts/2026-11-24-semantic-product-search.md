검색어 쿼리로 모호한 표현을 보냈을 때, 매칭되는 상품을 제대로 찾을 수 있을까요? 

보통 검색 기능은 상품명을 데이터베이스에서 조회하고 매칭되는 목록을 반환하는 로직을 가지고 있어요. 하지만 이 경우 사용자가 정확하게 상품명을 입력해야만 해당 키워드를 포함한 상품 데이터를 조회할 수 있다는 게 단점이죠. 

저는 Transformer.js 를 사용해서 검색 기능을 고도화하고자 하였어요. 
Geeknews 를 참고하여 아이디어를 떠올렸고, 참고한 글은 https://news.hada.io/topic?id=14299 여기에 있어요. 

Transformers.js는 서버 없이 브라우저에서 Transformers 모델을 실행하기 위한 라이브러리예요. Hugging Face의 Python transformers와 기능적으로 동등합니다. 모델 실행에는 ONNX Runtime을 사용하며, 브라우저 기본 실행은 WASM 기반 CPU라고 합니다. 

브라우저에서 모델을 실행하는 케이스는 어떤 게 있을까요? 대표적인 사례를 조사해보았어요. 

| 어떤 경우에 쓰나 | 실제 사례 | 브라우저에서 하는 이유 |
|---|---|---|
| **입력을 기기 안에 두고 싶을 때** | Firefox의 페이지 번역 | 사용자가 읽는 페이지 본문을 번역 서버에 보내지 않고 기기에서 번역해요. 언어 모델을 받아 두면 오프라인에서도 동작해요. [Mozilla 기술 블로그](https://blog.mozilla.org/en/firefox/firefox-146/) |
| **입력이 계속 들어오고 결과가 즉시 필요할 때** | Google Meet의 배경 흐림 | 카메라 영상은 프레임마다 사람과 배경을 구분해야 해요. Google이 공개한 웹 구현은 그 계산을 브라우저에서 수행해, 배경을 흐리는 데 매번 서버 응답을 기다릴 필요가 없어요. [Google Research](https://research.google/blog/background-features-in-google-meet-powered-by-web-ml/) |

모델은 서버에서 실행하거나, 별도의 추론 서버를 두는 게 일반적일 것 같아요. 하지만 브라우저에서 모델 실행하는 케이스를 공부해보니, 충분히 근거가 납득이 가네요. 데이터를 서버에 저장할 필요가 없거나, 영상 프레임처럼 브라우저에서 처리할 입력이 많고 빠르게 변화할 때 사용하네요. 우리 서비스에서는 위의 케이스가 적용되지 않지만, 프론트를 공부할 겸 구현해보았습니다. 다음에는 웹캠과 관련된 서비스를 만들어보고 싶네요! 

### 핵심 코드 
```

const options = { pooling: "mean", normalize: true }; // 정규화 

// 상품 목록을 받았을 때 한 번만 계산
const passages = products.map(p => `passage: ${p.name} ${p.description}`);
const vectors = (await encoder(passages, options)).tolist(); // 상품 벡터 정규화 

```
우리 검색의 핵심은 상품 설명은 한 번만 벡터로 만들고, 검색할 때 검색어와 가장 비슷한 작품부터 정렬하는 것이에요. 
브라우저 메모리에 있는 vectors 배열에 상품 벡터를 저장해두어요. 그래서 두 번째 검색부터는 준비해둔 상품 벡터를 재사용할 수 있고, 검색어 벡터만 새로 계산합니다. 

#### 벡터 준비 
우선 정규화를 통해서 벡터 길이를 1로 맞추고 방향을 그대로 유지해요. 정규화를 하는 이유는 상품 벡터와 검색어 벡터가 길이를 통일하고 얼마나 같은 방향을 가리키는 지로 점수를 매기기 위해서예요. 덕분에 벡터가 크다는 이유만으로 점수가 높아지는 걸 막을 수 있어요. 
예를 들어 [3, 4]는 오른쪽으로 3, 위로 4만큼 가는 화살표예요. 길이는 √(3² + 4²) = 5죠. 정규화할 때는 두 숫자를 모두 5로 나눠서 [0.6, 0.8]로 만들어요. 그러면 화살표 전체의 원래 크기를 1/5로 줄엿으니, 벡터 길이가 1이 됩니다. 가로와 세로의 비율이 여전히 3:4라서 같은 방향을 가리켜요.

벡터가 크면 방향이 덜 비슷한 상품도 1등을 할 수 있어서 정규화가 필요해요. 검색어 벡터가 [1, 0]이라고 해볼게요.

| 상품 | 정규화 전 점수 | 정규화 후 점수 |
|---|---|---|
| A `[1, 0]` · 검색어와 같은 방향 | `1×1 + 0×0 = 1` | `1` |
| B `[3, 4]` · 검색어와 비스듬한 방향 | `1×3 + 0×4 = 3` | `0.6` |

정규화 전에는 B가 3점으로 A를 이겨요. 그런데 B를 길이 1로 줄이면 [0.6, 0.8]이 되고, 점수는 0.6이에요. 이제 검색어와 정확히 같은 방향인 A가 1등이죠.

정규화 이후 점수는 우리 코드에서 중요하지는 않고, 핵심은 정규화를 통해서 벡터 길이를 1로 맞추는 것이에요. 다음 코드에서 코사인 유사도를 계산할 때 편리하게 벡터들의 내적만으로 코사인유사도를 계산하기 위해서 정규화를 합니다. 
```


// 검색할 때마다 실행
async function search(query) {
  const [q] = (await encoder([`query: ${query}`], options)).tolist(); // 검색어 벡터 정규화 

  return vectors
    .map((v, i) => ({
      id: products[i].id,
      // 상품 벡터(v)와 검색어 벡터(q)의 같은 위치 숫자를 곱해서 더하기 
      score: v.reduce((sum, value, j) => sum + value * q[j], 0),
    }))
    .sort((a, b) => b.score - a.score)
    .map(result => result.id);
}
```

#### 점수 계산 
위의 코드에서 스코어 계산 부분만 자세히 보면, 
```
// 상품 벡터(v)와 검색어 벡터(q)의 같은 위치 숫자를 곱해서 더하기 
      score: v.reduce((sum, value, j) => sum + value * q[j], 0),

```
스코어를 계산할 때 상품 벡터(v)와 검색어 벡터(q)의 같은 위치 숫자를 곱해서 차례로 더해요. 정규화를 통해서 두 벡터의 길이를 1로 맞췄으므로 이 값이 곧 코사인 유사도라서, 이 값에 따라서 sort 를 해요. 이유는 아래에 나옵니다. 

예를 들어볼게요. 
상품 벡터 v = [0.6, 0.8], 검색어 벡터 q = [1, 0] 을 넣으면 코사인 유사도는 `0.6`이에요.

| 몇 번째 칸? | 상품 값 `value` | 검색어 값 `q[j]` | 두 값을 곱하면 | 누적 합계 `sum` |
|---|---:|---:|---:|---:|
| 첫째 칸 `j = 0` | 0.6 | 1 | 0.6 × 1 = 0.6 | 0 + 0.6 = **0.6** |
| 둘째 칸 `j = 1` | 0.8 | 0 | 0.8 × 0 = 0 | 0.6 + 0 = **0.6** |

왜 이 합계가 코사인 유사도일까요? 원래 공식은 두 벡터의 내적 ÷ (상품 벡터 길이 × 검색어 벡터 길이)예요. 표에서 구한 합계 0.6이 내적이고, 두 벡터는 이미 정규화해서 길이가 각각 1이에요. 그래서 **`0.6 ÷ (1 × 1) = 0.6`**이에요.

상품마다 위의 계산 점수 계산 과정을 거치고, 이 점수에 따라 여러 상품의 순위를 결정해요. 
| 상품 | 정규화한 상품 벡터 | 검색어와 비교한 점수 | 순위 |
|---|---|---|---|
| 상품 A | `[1, 0]` | `1×1 + 0×0 = 1` | 1위 |
| 상품 B | `[0.6, 0.8]` | `0.6×1 + 0.8×0 = 0.6` | 2위 |

코사인 유사도는 두 벡터가 얼마나 같은 방향을 가리키는지 나타내는 값이에요. 결과적으로 검색어 벡터와 각 상품의 설명 벡터를 비교하고, 코사인 유사도가 높은 상품부터 정렬해요.

## 현재 아키텍처의 한계와 개선 방안 

현재 아키텍처에는 두 가지 한계점이 있어요. 한계점과 개선 방안을 함께 소개할게요. 

첫 번째는 상품 데이터가 방대해지면 벡터 생성으로 인해 시간이 지연된다는 점이에요. 현재 화면에서 상품 목록은 먼저 보여주고, 사용자가 검색창을 눌렀을 때 벡터 준비를 시작하는 방식이에요.** 검색 화면에서 동일한 search() 함수를 호출하도록 연결하면 두 번째 부터는 미리 저장해둔 상품 벡터를 재사용할 수 있어요. 하지만 상품이 몇만 개라면 첫 검색 한 번을 위해 꽤 오래 기다려야 할 수도 있겠죠. 저는 설계를 할 때 작게 쪼갤 수 있는 단계는 가능하면 작게 분리할 수록 좋다고 생각해요. 이 경우에도 상품 벡터 저장 -> 쿼리 조회 이 로직을 분리한다면, **상품 벡터를 저장하는 저장소는 별도로 두어 미리 상품 벡터를 저장해둘 수 있어요.** 미리 만들어둔 벡터를 불러오는 것은 별개의 기능이니까요. 기능을 담당하는 컴포넌트를 느슨하게 결합하는 방법이죠. 

두 번째는 **현재 구현에서는 페이지를 새로고침하면 상품 벡터가 사라진다는 점이에요.** 벡터 배열을 브라우저 메모리에 저장해두었기 때문이에요. 여기서 메모리는 사용자 기기의 RAM을 가리켜요. 브라우저가 페이지를 실행하는 동안 JavaScript 변수를 잠시 보관하는 공간이에요. **만약 새로고침 이후에도 상품 벡터를 재사용하려면, 계산한 벡터를 파일이나 저장소에 보관해두면 됩니다.** 예를 들어 json 파일에 저장하면, 이 파일은 디스크에 저장이 되고 브라우저가 그 값을 다시 읽어서 RAM 에 배열을 만들어요. 또 localStorage라는 브라우저가 사용자 기기에 데이터를 보관하는 저장소가 있어요. 이 저장소에 값을 쓰면, 브라우저가 그 값을 디스크에 보관하고 다시 읽을 수 있어요. 참고로 여기에 문자열만 저장할 수 있으니 배열을 JSON 문자열로 바꿔 넣고, 꺼낼 때 다시 배열로 만들면 돼요. 메모리와 디스크를 차이를 안다면, 이 문제를 쉽게 이해할 수 있을 거예요.
